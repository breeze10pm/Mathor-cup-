赛题10:30与用户报告的10:52/10:59时间线存在冲突。本报告保留两者，不自行把10:30解释成触发、报告或到达时刻；进一步解释需要原始通报的时间阶段和时区。秒数只用于情景计算，输入时间只有分钟精度。

均匀分布只是一种便于给出可读区间的“参考值”假设：硬约束范围仍是完整7分钟；在均匀假设下，两端各截去2.5%，得到约10分30秒后的中央95%情景区间。不得将该数值写成样本估计的95%置信区间，也没有声称其覆盖率为95%。敏感性表还列出90%与99%均匀情景区间。

## 条件预警规则

如果上游监测系统确认冰崩时刻为`t_detect`，可按沿线距离除以事件锚定表观速度给出口岸到达情景。以A/B候选路线分别按报告的10:52至10:59间隔反算基准速度，再乘以0.85、1.00、1.15作为敏感性参数，到达时间约为检测后6.09–8.24分钟。由于基准速度由同一事件反算，10:59吻合是校准构造，不是独立验证。它是冰崩起始到口岸的整条链平均速度，不等于已测的泥石流流速。

GFS/WRF起报时间2026-08-25 00 UTC到用户报告冰崩起始为26小时52分。这只是数值模式起报到事件的回溯间隔；没有产品公开时间，不能称作业务预警提前量。若假设设备恰在10:52即时识别冰崩，理论上有7分钟至报告到达，但这不是实际预警成绩。

## 复现与文件

在项目根目录、`mc-base`环境运行：

```console
python scripts/prepare_event_context.py
python scripts/build_question3_baseline.py
```

输出在 `output/question3/`：`question3_summary.json`、`question3_timeline.csv`、`question3_metrics.csv`、`question3_trigger_time_scenarios.csv`。路线和源点空间关系由 `output/event_context/event_context_summary.json` 提供。

## 升级所需

需要核实10:30、10:52、10:59各自对应的事件阶段、时间来源/时区和误差；补充泥石流触发监测时刻、天气预报发布时间与正式预警签发记录。要估计95%覆盖率，需要多个有可靠触发时间的独立事件和逐事件留出验证。时间资料未到前，均匀情景用于展示假设对区间的影响，不作为模型性能结论。
